# ComfyUI 插件设计说明

这份文档回答「除了那三条需求，还需要什么」。它按产品视角写：先定人、再定场景、最后定取舍。

## 一、谁在用，用来干什么

| 角色 | 场景 | 频率 | 在意什么 |
| --- | --- | --- | --- |
| 内容创作者 | 公众号/小红书配图、封面 | 每天数次 | 快、能改、能一次出多张挑一张 |
| 开发者 | 图标、占位图、UI 素材 | 偶尔 | 尺寸精确、可复现（种子） |
| 折腾党 | 试新模型、调 LoRA、跑自定义工作流 | 每周 | 模型/工作流可换、能看到真实进度 |

三类人共同点：**不想为了出一张图切走**。所以插件的核心不是「ComfyUI 客户端」，而是「在对话流里补一个出图动作」。

## 二、三条硬需求对应的设计

### 需求 1：设置里配置地址与模型

- 地址：默认 `http://127.0.0.1:8188`，接受 `host:port`、反代路径、`/api` 后缀（自动裁掉）。有「测试连接」按钮，回显版本与显卡 —— 用户填错时要立刻知道错在地址还是 token。
- 模型：**不手填**，从 ComfyUI 的 `/models` 拉真实清单。手填文件名是这类插件最常见的挫败点：名字错一个字符要等一次失败的生成才知道。清单拉到之后，预设缺模型直接标红并列出缺哪几个文件。
- token：写后不回显，只显示「已配置」。
- **模型不是孤立配置，而是「预设」的一部分**。因为 ComfyUI 的模型文件与节点图是绑定的：一个 `diffusion_models` 的 unet 需要配套的 `text_encoders` + `vae` + 正确的 `CLIPLoader.type`，随便换个文件名不会跑通。所以设置页的单位是预设，不是单个模型下拉框。

### 需求 2：对话窗口能调用

四个工具，而不是一个：

| 工具 | 为什么需要 |
| --- | --- |
| `comfyui_generate` | 主路径。默认**同步等待**，因为「给我画一张」应该在同一轮拿到图 |
| `comfyui_status` | `wait:false` 之后查进度；也用于「刚才那个图好了吗」 |
| `comfyui_cancel` | 生成 30 步的高清图时用户改主意了 |
| `comfyui_models` | 模型先查再用，避免拿不存在的预设去试错 |

关键决定：**图片作为图片块回传**。只返回路径的话，模型看不见自己生成的东西，用户问「这张图怎么样」它只能瞎猜。插件把 PNG 登记进 dsh 的附件存储，渲染时输出真正的 `image` 内容块，模型下一步就能看图。附件登记失败时降级为纯路径文本，不影响功能。

系统提示里写清「已接入 ComfyUI + 可用预设 + 默认尺寸」，让模型不必猜。

### 需求 3：右侧栏看队列与图片库

三段式，对应三种时间尺度：

- **生成**（现在）：正在做的那件事，进度条 + 取消。
- **队列**（接下来几分钟）：还有几张在排、谁在跑、清空排队。
- **图库**（过去）：所有产出，可搜索、收藏、下载、删除。

设计取舍：

- **进度必须是真进度**，不是假动画。ComfyUI 的 WebSocket 会发 `progress {value,max}`，直接映射成 `4/8`。只有拿不到时才退化为轮询。
- **页面隐藏就停止轮询**。侧边栏在后台每秒请求一次 `/api` 是纯浪费，还会在服务端日志里刷屏。
- **自动展开侧边栏默认关闭**。用户可能只是让模型「顺手画个图」，抢走右侧栏会打断他正在看的文件。

## 三、我额外加的东西，以及理由

### 1. 插件自带的本地队列（不是直接丢给 ComfyUI）

单卡一次只能跑一张图。如果直接把 5 个 prompt 丢给 ComfyUI，问题有三：

- `/queue` 只回 `prompt_id`，没有 prompt 文本和参数 —— 侧边栏没法显示「第 3 个在等的是什么」；
- 对话侧要取消「我刚才那个」，需要在 ComfyUI 的队列里认出它；
- ComfyUI 重启后队列清空，本地没有记录就完全丢失上下文。

所以 Host 自己持有一层队列，一次只下发一个。代价是 Host 需要跟踪状态机；收益是进度、取消、历史都归插件管。

### 2. 图片库落盘 + 索引，而不是只存 URL

ComfyUI 的 `/view` 只是读它自己的 output 目录。如果只存 URL：用户清一次 `output/`，历史全变裂图；换 ComfyUI 实例，图库全失效。

所以生成成功就**把 PNG 复制到插件自己的目录**，索引是 `index.json`。`saveDir` 可指向大盘或 NAS。收藏的图永不被保留策略清理 —— 「清理」误删用户挑出来的图是最伤信任的错误。

### 3. 保留策略（按天 + 按条数）

文生图会迅速堆满磁盘（一张 1024×1024 PNG 约 1.5MB，一天几十张就是几十 MB）。给两个正交的旋钮，默认都关闭 —— 不主动删用户数据，但让想删的人一键搞定。清理前有 `dryRun` 预演。

### 4. 种子可复现

`seedMode: fixed` + `seed` 让「刚才那张再来一次」成立。生成结果里永远回显实际使用的 seed，用户可以把它写进提示词让模型下次复用。

### 5. 批量出图

`batch 1..8` 一次出多张挑一张。这比让用户点八次「生成」体验好得多，而且 ComfyUI 原生支持 `batch_size`。

### 6. 自定义工作流 + 占位符

内置预设覆盖不了所有人的需求（有人要 ControlNet、有人要 IPAdapter）。允许粘贴 API 格式 JSON 并用 `{{prompt}}` `{{seed}}` 这类占位符，等于把整个 ComfyUI 生态接进来，而插件只需要知道怎么替换字符串。

### 7. 失败要能自己解释

每个错误都有 `comfyui/*` 码：
`offline` / `auth` / `invalid` / `model-missing` / `node-error` / `queue-full` / `timeout` / `canceled` / `settings-unavailable`。

UI 把码翻译成人话 + 下一步动作。例如 `model-missing` 直接跳「去设置 → 模型」，而不是只说「生成失败」。

## 四、明确不做的

| 不做 | 理由 |
| --- | --- |
| 内嵌 ComfyUI 节点编辑器 | 那是 ComfyUI 自己的活儿，重做一遍只会更差。要编辑就用 ComfyUI 的界面，插件只负责「跑」和「看结果」 |
| 多 ComfyUI 实例负载均衡 | 单卡是常态；多实例是机房需求，会显著复杂化队列与图片归属 |
| 图生图 / 局部重绘（本期） | 需要图片上传 + 输入图节点，是独立一轮功能；架构上 `custom` 预设已经能跑通这类工作流 |
| 自动把图发到微信/Notion | 已有 wechatpad / conversation-journal 插件负责分发，不该在这个插件里重复 |
| 假进度条 | 有真进度就用真的；没有就说「等待中」 |

## 五、还没做但值得排期的

按「用户痛感 ÷ 实现成本」排序：

1. **图生图 / 参考图** —— 用户上传一张图 + 提示词。`custom` 预设已支持，缺的是上传 UI 和 `LoadImage` 节点接线。痛感最高。
2. **提示词历史与一键复用** —— 图库里点一张图 →「用同样参数再画一张，换个主体」。成本很低。
3. **任务通知** —— 长任务（>60s）完成时，如果用户在别的会话，给一条轻提示。现在只有未读计数。
4. **尺寸比例预设** —— 16:9 / 9:16 / 1:1 / 3:4 一键切，而不是让用户算像素。成本极低，体验提升明显。
5. **图库导出** —— 打包下载选中图片 + 参数 JSON（便于交给别的工具复现）。
6. **索引换 SQLite** —— 图片过万时 `index.json` 会开始拖慢列表。当前上限 200 条内存 + 全量索引，暂时够用。
7. **多实例** —— 真有多卡再谈；届时队列要按实例分片，图片归属要带实例 id。

## 六、验证策略

产品承诺必须能被验证，所以测试分三层：

| 层 | 文件 | 证明什么 |
| --- | --- | --- |
| 纯逻辑 | `config` / `presets` / `format` | 归一化、工作流构建、占位符替换正确 |
| 契约 | `comfy-client` / `gallery` / `rpc` / `tools` / `service` | HTTP 与 WS 契约、路径穿越拒绝、白名单、状态机、附件回传 |
| 真机 | `host-live` | **真的生成了一张 PNG 并落盘**，尺寸/格式/图库寻址全对 |

真机测试是这条产品承诺的唯一硬证据：`tests/host-live.test.mjs` 会在本机 ComfyUI 上提交、跟进度、下载、校验 PNG 头与像素尺寸、确认图库索引可寻址。

## 七、图库为什么是「画廊」而不是列表

最初图库按任务分组、每张图裁成同样大小的方格。实机用一段时间后有两个明显问题：

1. **裁切毁掉构图**。文生图最常见的诉求之一就是不同的宽高比（16:9 封面、9:16 手机壁纸、1:1 头像）。`object-fit: cover` 把 9:16 的灯塔裁成方块，用户看到的和自己生成的不是同一张图。画廊模式保留原始宽高比，瀑布流布局（CSS `column-width` + `break-inside: avoid`）让高矮不一的图自然咬合，成本只是一条 CSS 规则，不需要测量 JS。
2. **分组让浏览变慢**。一组任务一个标题再套网格，等于把「浏览图片」变成「阅读目录」。画廊把图片本身放在第一位，任务信息退到查看器里 —— 那才是用户想细看的地方。

配套的全屏查看器补上列表做不到的事：

- `←`/`→` **跨任务**翻页并首尾环绕。如果要在一个任务的 2 张图里走到头再关掉重开，查看器就只是个大号缩略图。
- 显示完整提示词、负面词、尺寸、步数、种子、预设、时间 —— 这些是「复现一张图」必需的信息，网格里放不下。
- 收藏 / 下载 / 删除就地可用；删除后自动切到相邻图片，而不是留一个指向已删除文件的破图。

一个实现细节值得记下来：列数用 `column-width` 而不是 `column-count`。右侧栏只有约 400px 宽，但浏览器视口可能 2000px 宽；用视口媒体查询会在窄侧边栏里塞进三列，用容器相对的列宽才能自适应。

对应验证：`tests/format.test.mjs` 覆盖了扁平化与环绕索引的纯逻辑；浏览器回归用真实生成的 16:9 / 9:16 / 1:1 三张图确认瀑布流未裁切、查看器键盘导航与关闭后 `body` 滚动恢复。
